# High Level Steps for the Project

This document is the enriched Part 1 deliverable: each part below now has a substep checklist, tests, and success criteria. Checkboxes get checked off as work completes. Two hard sign-off gates exist: **after Part 1** (this document, before Part 2 starts) and **after Part 5** (the DB schema, before Part 6 starts).

Key architecture decisions this plan assumes (agreed with the user before this document was written):
- Auth is DB-backed (one seeded `users` row, hashed password), not string-literal comparison, via a plain random-token httpOnly session cookie + in-memory server lookup.
- The login gate is client-side: the static export always serves the same shell; the root page checks `GET /api/auth/me` and renders `LoginForm` or the board accordingly.
- The frontend's existing `useReducer`/`dispatch` pattern stays intact. A `HYDRATE_BOARD` action is added; `ADD_CARD` awaits the server (adopts the server-generated id); `UPDATE_CARD`/`DELETE_CARD`/`RENAME_COLUMN`/`MOVE_CARD` are optimistic with resync-on-failure.
- The AI chat's Structured Outputs schema is `{ reply: string, actions: Action[] }` (0..N actions per turn). The backend executes actions directly against SQLite and returns the fresh board — the client never interprets raw actions itself.
- Single Dockerfile, no docker-compose. Two OS scripts (`start.sh`/`stop.sh` for Mac+Linux, `start.ps1`/`stop.ps1` for Windows).
- Part 8/9 live-OpenRouter tests are `pytest.mark.live`, excluded from normal runs.
